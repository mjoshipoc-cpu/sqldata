What you are doing today is best described as prompt engineering (a handcrafted instruction prompt embedded in code). It becomes prompt tuning only if you run a systematic, measurable optimization loop over that prompt (or you tune model parameters via a tuning/fine-tuning method). In most client settings, you should call this “prompt optimization / prompt refinement with evaluation” unless you are actually doing parameter-level tuning. Is your current approach “prompt tuning”? Not by itself. A single static prompt string in code is a prompt template. It becomes “prompt tuning” when you: define a target schema + success metrics, run the prompt on a labeled test set, measure errors, revise the prompt in versions, re-test, and select the best-performing version with evidence. That is what you should document to the client. How to perform prompt tuning (practical, client-ready process) 1) Create a “golden dataset” (10–50 EMRs) For each EMR, prepare expected outputs: HbA1c numeric value (most recent) HbA1c DOS (apply your hierarchy) page number Diabetes Yes/No demographics fields if present This is your ground truth. 2) Define measurable acceptance criteria Examples (you can use these as KPIs): JSON validity rate: % responses parse successfully Schema compliance rate: all keys present, correct types HbA1c accuracy: exact match of numeric value HbA1c DOS accuracy: exact match (mm/dd/yyyy) Most recent logic correctness: correct selection when multiple results exist False positives: “ordered/recommended/scheduled” incorrectly marked as performed 3) Convert prompt into a cleaner, testable template Your prompt is strong, but it mixes multiple rules and contains a few conflicts: You say “only provide the details mentioned above” but also introduce generic rules like “Scheduled”. You say “Only provide JSON format” but don’t explicitly forbid any extra text before/after JSON. You ask DOS (visit date) and HbA1c_DOS (lab date) but the prompt sometimes suggests using DOS for HbA1c date—this increases confusion. Tuning step: tighten constraints and reduce ambiguity. 4) Run a controlled iteration loop (this is the “tuning”) Do this in versions (v1, v2, v3…), each with a changelog: v1: baseline (your current prompt) v2: enforce JSON-only + strict schema + null rules v3: add explicit negative rules for “target <7”, ranges, “ordered”, “plan” v4: add evidence snippets for HbA1c to improve auditability (optional) Each version is run on the same golden dataset and scored. 5) Add guardrails in code (post-processing) Prompt tuning alone won’t guarantee correctness. Add: JSON parse + schema validation date validation (mm/dd/yyyy) numeric validation for HbA1c (regex for decimals) reject ranges (“7.3–9.1”) and thresholds (“<7.0”) deterministically if invalid, re-ask model with an error-correction prompt (“Your JSON failed schema: … fix only …”) This materially improves client confidence.
