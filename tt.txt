## FHIR Ingest Pipeline — Unified FHIR Ingest/Persist Layer for Diagnostic Module

**Environment:** Python, Flask, MongoDB, `fhir.resources` (R4B / pydantic v1), JWT

**Overview:** A Flask-free, unit-testable ingest pipeline that takes a single
FHIR resource or a `Bundle` (transaction/batch/collection) from the HTTP edge
through parsing, resource-type dispatch, canonicalization against the FHIR R4B
model, and multi-layer validation (required fields, value-set bindings,
cross-element invariants), then hands validated resources to an append-only
versioned MongoDB store. Every failure at any layer resolves to the same
currency — an `OperationOutcome` with a matching HTTP status — so clients see
one consistent error contract across create, update, delete, read, search,
history, and vread. Supports the Diagnostic Module resource types
(`Observation`, `DiagnosticReport`, `ServiceRequest`, `DocumentReference`,
`ImagingStudy`) through a registry-as-data design, so adding a new resource
type is a data entry, not new pipeline code.

**Roles & Responsibilities:**
- Designed and built the three-band pipeline architecture (transport edge →
  Flask-free ingest core → storage layer) so business logic has zero Flask or
  database-driver dependencies and can be unit-tested standalone.
- Implemented the ingest sequence — parse → dispatch → canonicalize → validate
  — with `fhir.resources` (R4B) driving structural canonicalization and a
  custom invariant/value-set layer covering checks FHIR's model layer doesn't
  enforce (e.g. Observation `obs-6`/`obs-7`).
- Built the `Bundle` path (`transaction` / `batch` / `collection`) to reuse the
  exact single-resource dispatch/validate code per entry, with
  transaction-reject-whole and batch-partial-failure semantics.
- Designed the append-only versioned persistence model in MongoDB — one row
  per version, `IsCurrent`/`DeletedFlag` flags, partial unique indexes for
  race-safe create — giving history, vread, and soft-delete "for free."
- Implemented tenant isolation via per-client physical MongoDB databases,
  bound to the verified JWT `sub` claim.
- Added a resilience path for DB outages: writes degrade to disk-spooled JSON
  with a `202 Accepted` response instead of failing the request.
- Wrote a request-tracking layer (Mongo `Tracking` documents) recording every
  request's stage progression for audit and operational visibility.
- Authored architecture documentation (`docs/pipeline-flow.md`,
  `docs/request-flow.html`, `docs/observation-lifecycle.html`) and a review
  pass (`docs/pipeline-review.md`) identifying and prioritizing correctness
  and concurrency findings (connection reuse, deleted-id reuse, Bundle
  response-shape drift, identifier dedup).
- Built layered test coverage: per-stage unit tests (`tests/test_fhirpipeline_step*.py`),
  a no-DB/no-JWT end-to-end harness, and an in-memory-collection API test
  covering full CRUD + search + history.

## HEDIS Abstractor.ai — Automated HEDIS Clinical Data Extraction Pipeline

**Environment:** Snowflake Cortex AI, Claude Sonnet 4.5, Snowflake AI_PARSE_DOCUMENT,
Snowflake Cortex Vector Search, SQL, YAML

**Overview:** An automated healthcare data processing pipeline built on Snowflake
Cortex AI that analyzes Electronic Medical Records (EMRs) to evaluate patient
compliance with HEDIS quality measures. Uses a RAG (Retrieval-Augmented
Generation) architecture — embedding parsed EMR text into a vector store and
retrieving only the most relevant clinical sections per measure before LLM
extraction — to transform unstructured EMR PDF documents into validated,
structured HEDIS measure outcomes at scale.

**Roles & Responsibilities:**
- Built an automated PDF ingestion pipeline to detect new EMR files from a
  Snowflake stage and extract text using Snowflake's `AI_PARSE_DOCUMENT`.
- Implemented a RAG architecture — chunking and embedding parsed EMR text with
  Snowflake Cortex Vector Search to enable semantic retrieval of relevant
  clinical sections per HEDIS measure, reducing prompt size and improving
  extraction accuracy.
- Designed measure-specific LLM prompts, grounded in retrieved evidence chunks,
  to extract structured clinical information from unstructured EMR documents
  across multiple HEDIS measures.
- Implemented ICD code extraction to identify diagnosed conditions and map
  relevant codes from clinical documentation.
- Generated structured JSON summaries of patient demographics, diagnoses,
  medications, and other clinical details.
- Built a secondary LLM-based validation layer producing confidence scores and
  an evidence matrix linking extracted data back to the retrieved source
  chunks for auditability.
- Designed idempotent upsert logic in Snowflake tables to prevent duplicate
  records during reprocessing.
