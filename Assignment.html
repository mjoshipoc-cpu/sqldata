1. Structural validity (via fhir.resources library) Matches JSON against official FHIR R4B schema for the resource type. Flags unknown/misspelled resourceType. 2. Resource type mismatch If you validate as "Patient" but data says "Condition", flags immediately. 3. Required fields — now covers 19 resource types in config.py: Clinical: AllergyIntolerance, Condition, Procedure, FamilyMemberHistory, CarePlan, Goal, CareTeam Diagnostic: Observation, DocumentReference, ImagingStudy, DiagnosticReport, ServiceRequest Medication: MedicationDispense, MedicationAdministration, Immunization Administration: Patient, Practitioner, Organization, Location (correctly [] — no FHIR-mandated fields) 4. Choice-type required fields (new capability) — handles FHIR's [x] fields where one of several alternatives must be present, e.g.: Immunization: occurrenceDateTime OR occurrenceString MedicationAdministration: medicationCodeableConcept OR medicationReference, and effectiveDateTime OR effectivePeriod MedicationDispense: medicationCodeableConcept OR medicationReference 5. Value-set / allowed-code validation — 18 resource types, checking things like: Status codes (Observation.status, CarePlan.status, Goal.lifecycleStatus, etc.) Intent/priority (CarePlan.intent, ServiceRequest.priority) Nested coded paths (clinicalStatus.coding.code, reaction.severity) Location.mode, Immunization.primarySource (boolean check) 6. Common cross-resource fields — telecom.system, identifier.use, name.use checked on any resource type via COMMON_VALUE_SETS. 7. Bundles vs single resources — auto-detects Bundle vs standalone resource, validates each entry, aggregates valid_entries/invalid_entries/overall_valid. Still not handled (known gaps): No rules for resource types outside the 19 listed (e.g. Encounter, Medication) — those only get structural validation. No cross-resource reference resolution (doesn't check Patient/example actually exists in the bundle). No real terminology binding to code systems like SNOMED/LOINC — value sets are hardcoded strings.
